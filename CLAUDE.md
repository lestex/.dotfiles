# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal dotfiles + machine bootstrap for macOS only. Pure bash — no build system, no test framework, no package manifest. The "program" is a set of idempotent-ish provisioning scripts that install software and **copy** config files into `$HOME`.

## Commands

```sh
./install.sh                                       # set up this Mac from this checkout (safe to re-run)
./install.sh fonts themes                          # run only these steps; ./install.sh --list shows them
scripts/steps/80-fonts.sh                          # or run one step directly, from any directory
for t in tests/*-test.sh; do bash "$t"; done      # the tests; need macOS (theme-switcher's also an installed theme engine)
```

There is no lint tooling. CI (`.github/workflows/mac.yaml`) runs `./install.sh` on `macos-latest`, so **running the installer on macOS is the test**. It runs on pull requests touching `scripts/**`, `local/**`, `tests/**`, `.config/**`, `install.sh` or its own workflow file. Tests are `tests/*-test.sh`; mac CI runs them all after the installer (with `THEME_SWITCHER_TEST_REQUIRE_ENGINE=1`, so a missing theme engine fails rather than skips), and they can be run by hand on macOS. `theme-switcher-test.sh` uses a throwaway `HOME`, a fake terminal and a stub `osascript`; `install-test.sh` runs `install.sh` against fake checkouts with stub steps; `font-switcher-test.sh` uses a throwaway `HOME` and downloads Fira Mono to check that a just-copied, unregistered font is accepted; `tmux-open-link-test.sh` uses a stub `open` and drives a private tmux server through a real client with simulated Shift+clicks. None touches the real desktop, tmux server or installed software (tmux runs with `$TMUX` unset and a private `TMUX_TMPDIR`).

Each step sources `scripts/common`, which `cd`s to the repo root itself, so steps run from any directory.

## Architecture

**Entry point.** `install.sh` is the only entry point. It exits on anything but macOS, finds the checkout, then runs the steps in `scripts/steps/` — all of them in `NN-` order, or only the ones named as arguments (with or without the `NN-` prefix, in the order given; unknown names are rejected before anything runs; `--list` prints each step's line-2 summary). A failing step stops the run and names the step to re-run. Run from a checkout (a regular file whose directory has `scripts/steps`) it uses that checkout; run as the `bash <(curl ...)` / `curl | bash` one-liner it fetches the repo into `$DOTFILES_DIR` (default `~/.dotfiles`) with `curl` + `tar` — on a fresh Mac `git` is only a Command Line Tools stub until Homebrew installs them — and on later runs pulls a git checkout there or replaces a downloaded copy. The current directory never counts as the checkout under the one-liner. `DOTFILES_REPO` overrides the repo URL (a fork, or a local `file://` copy, as `tests/install-test.sh` uses).

**`scripts/common`** is sourced by every script and holds the color vars, `pretty_print`, the brew helpers and the pins that are not language versions (Alacritty, the theme engine). Language and tool versions (Python, Go, Terraform, Node, AWS CLI) are in `.config/mise/config.toml`, read by mise.

**Steps.** Each `scripts/steps/NN-name.sh` is independent and idempotent: it starts with a one-line summary on line 2, sources `scripts/common` (repo root, `XDG_CONFIG_HOME=~/.config`, `brew` on `PATH` via `load_brew_env`, `require_brew`, `pretty_print`, `brew_formulae`/`brew_casks`, the pinned versions), and skips work already done. There are no package manifests: each step lists the Homebrew formulae and casks it needs inline and installs them with `brew_formulae`/`brew_casks`, which run one `brew install` for those not in `brew list` yet (by plain name, so a tapped formula `owner/tap/name` and an alias like `gpg` must be written as Homebrew lists them, or they are reinstalled with a warning) and never upgrade. In order: `10-homebrew` (Homebrew, `brew update`), `20-tools` (command-line tools, among them git, bash 5, jq and fzf, which later steps and theme-switcher need), `25-apps` (desktop apps), `30-terminals` (Ghostty and kitty casks, tmux, and Alacritty from the official release DMG pinned by `ALACRITTY_VERSION` / `ALACRITTY_DMG_SHA256` — bumping it means updating both, the checksum being the asset `digest` GitHub publishes), `40-shell` (the Pure prompt, oh-my-zsh unattended, its plugins, `~/.zshrc` and `~/.zshrc.d`; after 20-tools because the oh-my-zsh installer needs real `git`), `45-neovim` (neovim, and LazyVim: clones `LazyVim/starter` into `~/.config/nvim` and drops its `.git`, as LazyVim's guide does, only when `~/.config/nvim` does not exist; plugins are left to the first `nvim` start, since a headless sync also compiles treesitter parsers, ~90 s; it also installs ripgrep, fd, lazygit and tree-sitter-cli for it, the last because nvim-treesitter needs the CLI and otherwise tries to fetch it through mason), `50-languages` (the `mise` formula, then `mise install --yes` with `MISE_GLOBAL_CONFIG_FILE` pointed at the repo's `.config/mise/config.toml`, since `70-configs` copies it into `~/.config/mise` only later; mise replaced pyenv, goenv, tfenv, nvm and the node formula, downloads prebuilt binaries — Python too, no compile — and skips what is installed, so a re-run takes milliseconds; versions are prefixes like `"3.14"`, resolved to the newest match at install time; `idiomatic_version_file_enable_tools` keeps projects' `.python-version`/`.go-version`/`.terraform-version`/`.nvmrc` working; CI passes `GITHUB_TOKEN` so mise's GitHub lookups are not rate-limited), `55-cloud` (gcloud-cli, Kubernetes tools, podman), `60-vscode` (the VS Code cask and the extensions listed in it not yet in `code --list-extensions`; skipped when there is no `code`; creates the settings folder, which exists only once VS Code has run), `70-configs` (`.config/*` into `~/.config`, the `@BREW_PREFIX@` substitution, tpm, `tmux-open-link`, vifm colors), `75-hotkeys` (the Hammerspoon cask, pointed with `defaults write org.hammerspoon.Hammerspoon MJConfigFile` at `~/.config/hammerspoon/init.lua`, then started unless `CI` is set; the config binds Cmd+Ctrl+T/B to launch-or-focus the terminal and browser — not Cmd+T/B, which apps own — takes the terminal from `local/bin/terminal-switcher` (installed by this step; `terminal-switcher ghostty|alacritty|kitty`, or no argument for an fzf pick, writes the lowercase name to `~/.local/state/terminal-switcher/current`, which the config reads on every press and maps to the app name, so a change needs no reload; `tests/terminal-switcher-test.sh` covers it in a throwaway `HOME`), reads other overrides from `~/.config/hammerspoon/local.lua`, which is not in the repo so `70-configs` never overwrites it (a file, not an env var, because GUI apps get no shell environment), makes its own windows follow macOS Dark/Light via `AppleInterfaceThemeChangedNotification`, reloads itself on any `.lua` change, and turns on launch at login), `80-fonts` (the Nerd Font casks, font-switcher, default font), `90-themes` (theme-switcher, the pinned engine, default theme, btop/Neovim links, the VS Code theme). Order matters where noted, and fonts/themes come after configs because the copied terminal configs include their generated files. Adding a step means a new numbered file with the same header; `install.sh` picks it up. `10-homebrew` evals `brew shellenv` after a fresh install itself; CI runners ship with brew, so CI never exercises that branch.

**Third-party taps need explicit trust.** Homebrew 6 refuses to load formulae from non-official taps unless they are trusted (`HOMEBREW_REQUIRE_TAP_TRUST` defaults to `true`), and the trust store is `$XDG_CONFIG_HOME/homebrew/trust.json` — which `scripts/common` points at `~/.config`, so a developer's manual `brew trust` (stored in `~/.homebrew/trust.json`) does *not* apply under the installer. Nothing here uses a third-party tap now; one added later needs `brew tap` plus `brew trust --tap` in `steps/10-homebrew`, or both the installer and CI will fail.

**Configs are copied, not symlinked.** `.config/*` → `~/.config` (except `zsh`), `.config/zsh/.zshrc` → `~/.zshrc` and `.config/zsh/.zshrc.d/*.zsh` → `~/.zshrc.d/` (`.zshrc` holds only oh-my-zsh and its plugins, then sources `~/.zshrc.d/*.zsh` in name order: path, languages (`mise activate zsh`, cargo), cloud, and the Pure prompt last (configured with `zstyle` there, colors as ANSI names only so it follows theme-switcher's palette); new shell settings go in a numbered file there, not in `.zshrc`; `40-shell` records the names it installed in `~/.local/state/dotfiles/zshrc.d` and removes one the repo no longer has, so renaming or merging drop-ins never leaves a stale one sourced), VS Code settings → the OS-specific application-support path (`.config/code/settings.json` carries no `workbench.colorTheme`; `steps/90-themes` re-selects the theme after the copy). Consequences:
- Editing `~/.config/...` does not flow back to the repo. Edit the repo file, then re-run `./install.sh`.
- Re-running the installer overwrites local tweaks under `~/.config`, `~/.zshrc` and the repo's files in `~/.zshrc.d`; other files in `~/.zshrc.d` are kept, so machine-local shell settings belong there.
- Directories cloned into `~/.config` by the scripts (vifm colors, tmux tpm) are guarded by existence checks and are not tracked here.
- Two files are templated rather than copied verbatim: `.config/ghostty/config` and `.config/alacritty/alacritty.toml` hold a `@BREW_PREFIX@` placeholder (the tmux path each terminal launches; kitty runs the login shell and uses its own tabs) that `steps/70-configs` rewrites with `sed` after the copy, because a terminal needs an absolute command path (GUI launches inherit no shell `PATH`) and the Homebrew prefix differs by architecture.

**Theme switching (macOS) runs an external theme engine in place.** `local/bin/theme-switcher` (installed to `~/.local/bin` by `steps/90-themes`) reads palettes (`themes/*/colors.toml`), templates (`default/themed/*.tpl`) and the engine's color-resolver, OSC and template-renderer scripts from a managed engine checkout — nothing from it is copied into this repo. `steps/90-themes` runs `theme-switcher engine install "$THEME_ENGINE_REF"`: a shallow, partial (`--filter=blob:none`), sparse fetch of `bin/`, `default/themed/` and `themes/` minus `themes/*/backgrounds/` (~26 MB) into `~/.local/share/theme-switcher/.engine`, at the full commit SHA pinned in `scripts/common` (a no-op when already there). Wallpapers are read from git on demand when a theme is first used, so only themes in use are downloaded. Bump `THEME_ENGINE_REF` deliberately: CI tests theme-switcher against the pin, which is what catches upstream renaming the engine's internals. `THEME_SWITCHER_ENGINE` points theme-switcher at a different checkout (e.g. a full clone for development); its wallpapers are then read from disk. The engine's own name (its script prefix, the `<NAME>_PATH` variable it reads, the dirs its renderer writes, and the default checkout path) is set once, as `ENGINE_NAME` in `local/bin/theme-switcher`; keep it out of every other file. The test detects the engine with `theme-switcher engine` rather than repeating its path. Those scripts are `#!/bin/bash` (3.2 on macOS) and call each other by name, so the wrapper re-execs itself under Homebrew's bash 5 and runs them through PATH shims. The renderer hardcodes its staging and user-template dirs under `$HOME`, so it runs with a scratch `HOME` whose two dirs symlink to theme-switcher's own; all state stays under `theme-switcher` paths. The wrapper adds only the macOS parts: staging into `~/.local/state/theme-switcher/current/theme/`, refusing a theme if any `{{ ... }}` survives rendering, repainting running terminals by writing OSC sequences to each terminal child's TTY (`pgrep -P` + `ps -o tty=`, no `/proc`), and the desktop picture via `osascript`. Ghostty (`config-file`), Alacritty (`import`, reloaded automatically) and kitty (`include ${HOME}/...`, sent `SIGUSR1`) include the generated files; Ghostty is never signalled, since it has no external reload on macOS. tmux follows in two ways: `.config/tmux/tmux.conf` styles its status bar and borders with ANSI color names only (never hex), which resolve through the terminal palette; and on each switch theme-switcher sets tmux's `window-style`/`window-active-style`/`cursor-colour` from the palette, writes the OSC palette to every pane's pty (panes are separate ptys the terminal repaint does not reach), sets `COLORFGBG` (dark/light) globally and per session, and refreshes clients. It uses `$TMUX`'s server when run inside tmux; the test drops `$TMUX` and uses a private `TMUX_TMPDIR`, so it never touches a real tmux server. btop follows as omarchy does: theme-switcher keeps `~/.config/btop/themes/current.theme` a symlink to the active theme's generated `btop.theme` (never replacing a real file there) and sends running btops `SIGUSR2`, which reloads config and theme (verified on btop 1.4.7); `steps/90-themes` points `btop.conf` at it by changing only its `color_theme` line to `"current"` (or writing a minimal `btop.conf`), and warns if btop is running, since btop rewrites `btop.conf` on quit. Neovim (LazyVim) follows the same way, plus live: theme-switcher keeps `~/.config/nvim/lua/plugins/theme.lua` a symlink to the active theme's `neovim.lua` (a lazy.nvim spec naming the theme's colorscheme plugin, or `aether.nvim` with the palette; only when `lua/plugins` exists; never replacing a real file), and for each running Neovim found as a socket `$TMPDIR/nvim.$USER/*/nvim.<pid>.0` (or under `$XDG_RUNTIME_DIR`) sends `--remote-expr` running `NVIM_APPLY_LUA` (written to `~/.cache/theme-switcher/nvim-apply.lua`): load each spec plugin through lazy if known, else prepend its dir under lazy's root to `runtimepath`; call `require(main or name).setup(opts)` when the spec has opts; then `:colorscheme` LazyVim's choice. If a plugin is not installed it returns `missing:`, and a background `nvim --headless "+Lazy! install" +qa` (given a private `TMPDIR`, so its own socket is not mistaken for a session) installs it, then re-applies everywhere. omarchy itself has no live reload. `steps/90-themes` creates the link and adds `lua/plugins/theme.lua` to the Neovim config repo's `.gitignore`. torrnado (the user's own TUI torrent client) follows the btop pattern with a template this repo ships rather than the engine: `.config/theme-switcher/themed/torrnado.toml.tpl` is copied by `70-configs` into theme-switcher's user-template dir, so every switch renders `torrnado.toml`; theme-switcher links `~/.config/torrnado/themes/current.toml` to it only when `~/.config/torrnado` exists (never replacing a real file), and `steps/90-themes` sets the top-level `theme` value in an existing `config.toml` to `"current"` (value only, comment kept; inserted at the top if absent, since an appended key would fall into the last TOML table) and re-renders the current theme once if it predates the template. torrnado itself re-reads the active theme file when it changes (its PR #128), so no signal is sent. VS Code follows as omarchy does: a theme's `vscode.json` (`{"name", "extension"}`, engine and hand-written themes only — installed themes have it dropped, since an extension is arbitrary code) names a Marketplace extension, installed with `code --install-extension` if `code --list-extensions` lacks it (in the background on a switch; `theme-switcher vscode` waits) and then selected; otherwise a local extension `~/.vscode/extensions/theme-switcher-theme` (a `package.json` plus a symlink to the generated `vscode-theme.json`, registered in `~/.vscode/extensions/extensions.json` with `jq`) contributes it under two labels, and each switch selects the other one, because VS Code does not re-read the file of a theme that stays selected. `workbench.colorTheme` is edited in place in `~/Library/Application Support/Code/User/settings.json` with BSD `sed`/`awk`, since that file is JSONC; names and extension IDs are validated as omarchy does. VS Code watches `settings.json`, so open windows switch without a signal. `THEME_SWITCHER_APPS` (default `btop nvim code`) lists apps to reload; tests set it empty so they never signal a real btop or Neovim or touch VS Code; `tests/nvim-theme-test.sh` reloads a headless Neovim with a fake colorscheme plugin in a private `TMPDIR`; `tests/vscode-theme-test.sh` uses a stub `code` in a throwaway `HOME`. The chosen background is a plain-text path in `current/background` (empty = a solid PNG in the palette background color); wallpapers are imported into `~/.local/share/theme-switcher/<theme>/backgrounds/`, never committed here.

**macOS appearance.** `set` (and `theme-switcher appearance`) also applies the theme to macOS: Dark/Light mode through System Events from the theme's `mode`; `AppleAccentColor` from the theme accent (`macos_accent_for`: 0 red … 6 pink only when the accent is saturated, ≥ 0.25, and within 22° of that accent's hue, because macOS's accents are all vivid; anything muted or in between, e.g. rose-pine's teal, gets -1 graphite; graphite also sets `AppleAquaColorVariant` 6, else 1); and `AppleHighlightColor` as the exact accent tinted 60% toward white, because the highlight shows behind selected text in every app, light pages included, where a theme's dark `selection` color would be unreadable. It then posts `AppleColorPreferencesChangedNotification`/`AppleAquaColorVariantChanged` so running apps redraw. The menu bar cannot be colored. `THEME_SWITCHER_NO_DESKTOP=1` skips this along with the desktop picture (the installer's first run and most tests); `theme-switcher-test.sh` stubs both `osascript` and `defaults`, since `defaults` writes the real user's preferences whatever `$HOME` is.

**Community themes.** `theme-switcher catalog|install|remove|update` work with the engine project's theme gallery (`CATALOG_URL`, built from `ENGINE_NAME`; each gallery entry is an `<a href="https://github.com/…">` around the theme's screenshot and name). `install <name|url>` resolves a gallery name to its repo, accepts only `https://`, `ssh://`, `git@host:` and `file://` URLs (no `-` prefix, no `<helper>::`), clones `--depth 1` under git's own `protocol.allow=never` + https/ssh/file allowlist into a staging dir, then into `~/.config/theme-switcher/themes/<name>` (name = repo name lowercased minus the `<engine>-` prefix and `-theme` suffix, restricted to `[a-z0-9_][a-z0-9._+-]*`), and applies it. It never replaces a theme directory that is not a git clone. A theme dir with `.git` (and not a symlink) is untrusted: staging copies it without `*.lua`, `alacritty.toml`/`foot.ini`/`ghostty.conf`/`kitty.conf`, `vscode.json` or any symlink, at any depth (`INSTALLED_THEME_DENIED`), names what it dropped on stderr, and derives `colors.toml` from a lone `alacritty.toml` in a scratch dir via the engine's colors-from-alacritty script. Hand-written themes (no `.git`) are trusted in full. Installed and hand-written themes use the images in their own `backgrounds/` in place (regular files only); only engine themes are imported into `~/.local/share`. `tests/theme-catalog-test.sh` covers this offline with a fixture gallery and hostile/legacy `file://` repos.

**Theme picker.** `theme-switcher pick` lists themes in fzf (starting on the current one) with `theme-switcher preview {-1}` as the preview command, and applies the selection; `pick --catalog` lists the gallery and installs the selection. `preview <name>` draws the theme's palette with 24-bit escapes on its own background (16 ANSI swatches, a prompt, code and a selection sample, padded to `$FZF_PREVIEW_COLUMNS`), plus, in Ghostty and kitty only, its `preview.png` above that as a real image (`kitten icat --unicode-placeholder`, as fzf's own preview script does, so it also works through tmux with `allow-passthrough on`). Other terminals, i.e. Alacritty (no image protocol), show the palette only: a text-block rendering was tried and dropped as too coarse. The terminal is taken from `TERM`, or inside tmux from `#{client_termname}`, since tmux's `TERM` hides it. `kitten` needs a controlling terminal, so it only draws under fzf or a pty, not in a bare script. `preview --repo <github url>` fetches only `colors.toml` and `preview.png` from raw.githubusercontent.com (falling back to deriving colors from `alacritty.toml`) into `~/.cache/theme-switcher/catalog/<owner>__<repo>/`, without cloning; only `https://github.com/<owner>/<repo>` URLs are fetched. fzf comes from `steps/20-tools`; `kitten` from the kitty cask (`steps/30-terminals`). `tests/theme-picker-test.sh` drives the real picker through a pty.

**Font switching (macOS).** `local/bin/font-switcher` (installed to `~/.local/bin` by `steps/80-fonts`, plain bash 3.2-compatible) writes the chosen family and size (`set <family>`, `size <points>`, default 14) into `~/.local/state/font-switcher/current/{ghostty.conf,alacritty.toml,kitty.conf}`, which the three terminal configs include — so the main configs set no font family or size, and the choice survives the installer re-copying them. It lists and validates fonts through AppKit via `osascript -l JavaScript`; a family counts as monospace when `i`, `M`, `W` and `.` share one advance width, because Nerd Font "Liga" builds such as Liga SFMono leave the fixed-pitch flag unset. Names are matched case-insensitively and restricted to `[A-Za-z0-9 ._+-]`, since they are written into three config syntaxes. `steps/80-fonts` installs a set of Nerd Font casks to choose from (JetBrainsMono, Caskaydia, Meslo, FiraCode, VictorMono, Bitstrom Wera, Iosevka) and Liga SFMono (`font-sf-mono-nerd-font-ligaturized`; SF Mono is Apple's and not redistributable, so it is never committed here — the step first removes copies an older installer put in `~/Library/Fonts`, since the cask refuses to install over them), which `steps/80-fonts` sets on first run. macOS registers new files in `~/Library/Fonts` in the background, so on a fresh Mac the font just copied is not listed yet; when a requested family is not found, font-switcher registers the files in `$HOME/Library/Fonts` with CoreText at process scope for that one lookup (nothing persists) and tries again. Alacritty applies a change by itself, kitty gets `SIGUSR1`, Ghostty needs Cmd+Shift+, or a new window. `font-switcher pick` lists the monospace families in fzf (starting on the current one); its preview, `font-switcher preview <family>`, shows a sample rendered to PNG by AppKit through JXA (`NSFontManager` font, `NSAttributedString` drawn into an `NSImage`, cropped to the text, in the current theme-switcher theme's background/foreground read from its `colors.toml`), cached in `~/.cache/font-switcher/<family>-<bg>-<fg>.png` and shown with `kitten icat --unicode-placeholder` in Ghostty and kitty (same terminal detection as theme-switcher); elsewhere it shows text only, since a terminal can only draw its own font. Both list the family's styles. Still bash 3.2-compatible.

**Links under tmux open with Shift+click in every terminal.** kitty and Alacritty keep Shift+click for themselves while tmux has the mouse and open links natively. Ghostty can only open links with Cmd (its `link` modifier is not configurable in 1.3), and with `mouse-shift-capture = false` that meant Cmd+Shift+click; instead it has `mouse-shift-capture = true`, so Shift+click reaches tmux, whose `S-MouseUp1Pane` binding runs `local/bin/tmux-open-link` with the OSC 8 link (`#{mouse_hyperlink}`), the line (`#{mouse_line}`) and column (`#{mouse_x}`, pane-relative, 0-based). Values are shell-quoted with `#{q:}`, which drops an empty value, so the binding passes `-` for none. The helper opens only http/https/file URLs, as one argument to `open`. `tmux.conf` also adds the `hyperlinks` terminal feature, without which tmux drops OSC 8 links.

**Shared terminal defaults.** Ghostty, Alacritty and kitty share one set of defaults — padding 14, no decorations, block cursor without blink (shell integration told not to restyle it), no close prompt, Shift/Ctrl+Insert paste/copy, Shift+Enter and Alt+Shift+Enter sent as CSI-u (`13;2u` / `13;4u`). When changing one terminal's behavior, keep the other two matching. Ghostty and Alacritty launch tmux; kitty keeps the login shell and its own tabs (bottom powerline bar, cmd+1..0, cmd+t/n).

## Conventions

- Scripts use `set -e` and wrap every install in an existence check with a `pretty_print "${yellow}...already installed, skipping${neutral}"` branch. Follow that pattern so re-running the installer stays cheap and CI-safe.
- `.editorconfig`: 2-space indent, LF, final newline.
- User docs are hand-maintained: `README.md` is short (install, everyday commands, links); the detail is in `docs/` — `installer.md`, `themes.md`, `fonts.md`, `terminals.md`, `shell.md`, `troubleshooting.md`. Update the page a change affects in the same change: a behavior, command, key or known problem. The software table in `docs/installer.md` mirrors the package lists in `scripts/steps/` (and the pinned versions in `scripts/common`). The steps, not the docs, are the source of truth.
